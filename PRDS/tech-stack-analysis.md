# 一帧.life 技术栈分析

> 本文档记录项目技术选型的决策过程、优劣势分析及改进建议。
> 完整项目文档见 `./project-document.md`

---

## 一、选型决策

### 1.1 为什么选 Astro？

| 考量 | 说明 |
|------|------|
| **内容为主** | 博客以 Markdown 文章为主，Astro Content Collections 提供类型安全的内容管理 |
| **性能优先** | 零 JS 默认，静态 HTML 输出，首屏加载极快 |
| **SEO** | 静态生成对搜索引擎友好，无需 SSR 配置 |
| **Markdown 原生** | 文章以 `.md` 文件形式存储，便于版本控制和 Obsidian 编辑 |

### 1.2 为什么用纯 CSS？

| 考量 | 说明 |
|------|------|
| **设计自由度** | Decora 风格需要精细控制每个元素的视觉表现，手写 CSS 更灵活 |
| **无构建开销** | 无需处理 Tailwind 等工具链的编译时间 |
| **零依赖** | 避免引入不必要的 CSS 框架，减少依赖维护负担 |

---

## 二、优势分析

| 方面 | 说明 |
|------|------|
| **Astro Islands 架构** | 仅在需要交互的组件（照片墙）注入 JS，其余页面零 JS 运行时 |
| **Content Collections** | Zod Schema 校验 + TypeScript 类型推导，编译时安全 |
| **Vercel 零运维** | Git push 即部署，无需配置 CI/CD |
| **纯 CSS 可控性** | `--deco-*` 变量系统便于主题管理，scoped styles 避免冲突 |
| **Obsidian 兼容** | Markdown 文章可用 Obsidian 编辑，`.obsidian/` 已 gitignore |

---

## 三、局限与改进方向

### 3.1 当前局限

| 问题 | 影响 |
|------|------|
| 无现代化 CSS 工具 | 样式复用率低，响应式断点管理分散 |
| 无搜索/评论/RSS | 缺少互动功能 |
| 照片管理手动 | `photos.json` 需手动维护 |
| 资源未优化 | 视频背景 11MB、Hero 背景 1.9MB 未压缩 |
| 缺少 ESLint/Prettier | 代码风格一致性依赖手动维护 |

### 3.2 改进路线图

| 阶段 | 内容 | 优先级 |
|------|------|--------|
| **短期** | 图片压缩、字体加载优化、添加 RSS、配置 Prettier | 高 |
| **中期** | Pagefind 搜索、Giscus 评论、照片管理自动化 | 中 |
| **长期** | Headless CMS、国际化、性能监控 | 低 |

## 四、性能预算

| 指标 | 目标值 |
|------|--------|
| 首屏 JS 体积 | < 50KB (gzip) |
| 动画帧率 | ≥ 60fps |
| 交互响应时间 | < 100ms |
